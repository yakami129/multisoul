# Chat 长对话性能优化 SPEC

**版本**: 1.0  
**日期**: 2026-05-24

---

## 1. 背景

用户打开已有 Chat 对话时感到明显变慢，怀疑原因是历史消息过多。当前实现会在进入 `Chat Detail` 时请求该会话的完整消息列表，并在移动端一次性保存和渲染可展示消息。长对话中，网络传输、JSON 解析、Zustand 数组替换、Markdown/图片/工具调用渲染都会叠加，导致首屏打开慢、滚动和输入不稳定。

本规格聚焦 **几百条到 800 条消息** 的真实长对话场景，目标是让 Chat 继续保持“实时工作现场”的体验，而不是把完整历史一次性塞进页面。

---

## 2. 目标

- 800 条历史消息内，打开已有对话后 **1 秒内看到最近消息，输入区可用**
- 默认进入最新消息底部，符合聊天软件心智
- 首屏只加载最近一段历史，旧消息向上滚动按需加载
- 长历史滚动时保持流畅，不因 Markdown、图片、工具调用或决策卡片一次性渲染而卡顿
- Activity 跳转到 pending 决策时，即使决策不在最近消息中，也能定位到对应卡片
- REST/WS 数据一致：打开页使用分页历史，运行中继续通过 WebSocket 追加新消息

---

## 3. 非目标

- 不做上万条消息的完整历史浏览体验
- 不做 Chat 历史全文搜索
- 不做消息摘要、折叠归档或 AI 自动总结
- 不引入中心化后端或云端缓存
- 不要求本阶段实现移动端 SQLite 消息缓存
- 不重写 Chat 视觉风格和消息内容类型

---

## 4. 用户体验

### 4.1 默认进入最新上下文

用户打开已有 Chat 时，页面应优先展示最近消息并停在底部。输入区、状态 Badge、停止按钮等当前工作流能力必须可用。

首屏不需要展示完整历史。页面顶部应支持继续加载更早消息，但不需要用醒目的说明打断用户。

### 4.2 向上加载旧消息

用户向上滚动接近顶部时，Chat 自动或通过轻量入口加载更早消息。加载完成后应保持滚动位置，不应突然跳到底部或跳到错误位置。

当已加载到最早消息时，继续向上滚动不再重复请求。

### 4.3 实时消息追加

对话运行中，新消息仍通过 WebSocket 追加到当前 timeline。若用户停留在底部，新消息到达后可自动滚到底部；若用户正在阅读旧消息，不应强制抢滚动位置。

### 4.4 Activity 决策定位

用户从 Activity 点击待处理决策进入 Chat 时：

1. 若目标决策已在当前加载窗口内，直接滚动到该卡片
2. 若目标决策不在最近窗口内，Chat 应请求目标消息附近的窗口
3. 页面加载后直接定位到该决策卡片
4. 定位期间仍应保留返回、状态展示和基础错误反馈

---

## 5. 功能需求

### 5.1 消息历史分页

后端消息列表接口必须支持“最近 N 条”和“某条消息之前 N 条”的分页能力。移动端打开 Chat 时默认请求最近一页，而不是全量历史。

建议默认页大小：

- 首屏最近消息：15 条
- 向上加载旧消息：50 条
- Activity 定位窗口：目标消息前后各一段，窗口总量不超过 100 条

具体参数名由实现计划决定，但必须表达以下语义：

- `limit`: 每次最多返回多少条消息
- `before_seq`: 返回某个 seq 之前的旧消息
- `around_seq` 或等价机制：返回目标消息附近窗口
- 响应能让移动端判断是否还有更早消息

### 5.2 移动端虚拟列表

Chat Detail 不应再用一次性渲染整个 transcript 的方式承载长对话。消息 timeline 必须使用虚拟列表能力，只渲染当前窗口附近的消息。

虚拟列表必须支持：

- 初始停在底部
- 顶部触发加载旧消息
- 追加实时消息
- 保持滚动锚点
- 支持 `ask_question` 定位
- 支持图片、Markdown、Mermaid、工具调用和等待态气泡

### 5.3 消息合并与去重

移动端需要把分页结果、Activity 定位窗口和 WebSocket 新消息合并到同一个会话消息集。合并必须以稳定消息身份去重，不能因为重复加载同一 seq 导致重复气泡。

如果分页加载到的旧消息和 WebSocket 追加消息出现交叠，应保留一条权威消息，并保持 seq 顺序。

### 5.4 渲染预算

长消息、Markdown 表格、代码块、图片、Mermaid 图等重内容不应阻塞首屏可用。首屏优先展示最近普通消息；重内容可在可见时渲染或延迟加载已有懒加载组件。

### 5.5 错误和离线

分页请求失败时，当前已加载消息不能被清空。页面应允许用户重试加载旧消息。若 endpoint 离线，保持现有 OFFLINE 体验。

---

## 6. 验收标准

- [ ] 构造 800 条历史消息的会话，打开 Chat 后 1 秒内能看到最近消息且输入区可用
- [ ] 首屏请求不会返回完整 800 条历史，只返回最近分页窗口
- [ ] 向上滚动可加载更早消息，且加载后滚动位置稳定
- [ ] 已加载到最早消息后，不会继续重复请求旧消息
- [ ] WebSocket 新消息能追加到当前 timeline，且不会和分页消息重复
- [ ] 用户阅读旧消息时，新消息到达不强制抢滚动；用户在底部时可自动跟随最新消息
- [ ] Activity 跳转到不在最近 15 条内的 pending 决策时，能加载目标附近窗口并定位到卡片
- [ ] 图片、Markdown、Mermaid、工具调用、决策卡片在虚拟列表中仍正常展示
- [ ] 分页请求失败不会清空当前消息，并提供可恢复路径
- [ ] Mobile typecheck 通过
- [ ] CLI 测试通过

---

## 7. 风险与约束

- `Chat Detail` 当前文件接近单文件 500 行上限；实现时若继续增长，应拆分分页状态、列表渲染或滚动定位逻辑
- CLI 消息表需要适合按 `conversation_id + seq` 查询；若缺少索引，分页接口可能仍慢
- Activity 定位需要知道目标 ask 对应的 seq；如果当前数据模型只保存 ask id，需要补齐查找能力
- Markdown/Mermaid 渲染成本可能独立于分页存在，必要时在实现计划中增加可见区域延迟渲染
- 本阶段不做移动端持久缓存，因此冷启动仍依赖本地 CLI API 可用性
